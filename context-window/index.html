The Context Window

Claude's working memory for your session — and it's finite. Knowing how it fills, when to compact, and how to save your work first is the difference between a smooth long session and a frustrating one.

⚡ In 30 seconds

The context window is Claude's working memory for a session — measured in tokens, not messages. Watch it as it grows, compact at the right moments to keep going, and — because compaction is lossy — save anything important to a document, a memory, or a skill before you compact.

What is a context window?

Picture a whiteboard Claude works at during your session. Everything currently in play is written on it: the system instructions, every message you've sent, every reply Claude has given — plus any files, PDFs, images, and tool or search results you've pulled in. That whiteboard is the context window, and it's how Claude "remembers" what you're working on.

It's measured in tokens (roughly ¾ of a word each), not words or messages. A long PDF can cost thousands of tokens; a quick question costs a handful. And the whiteboard has edges — once it's full, something has to give.

A useful mental model comes from AI researcher Andrej Karpathy, who likens an LLM to a computer: if the model is the CPU, the context window is the RAM — fast, working memory that holds what you're actively thinking about, but limited in size and wiped when the session ends.

Not all windows are the same size

Different models ship with different context-window sizes, and some offer extended long-context modes. A bigger model is a bigger whiteboard — it can hold more of your documents and history at once. Which one you're using affects how much room you have to work with, so it's worth knowing your model. (See Choosing Your Model.)

Bigger isn't always better

A larger window sounds like a pure win. It mostly is — but there are real trade-offs.

The upside:

  • More documents and conversation history in play at once.
  • Fewer restarts on long, multi-step work.
  • Whole-document analysis instead of feeding things in piece by piece.

The catch:

  • Cost & speed. More tokens in play means slower, pricier turns — every turn re-reads the window. (More in Tokenomics.)
  • Context rot. Quality and recall degrade as the window fills, well before you hit the hard limit. The advertised size isn't the same as the comfortably usable size.
  • Lost in the middle. Models tend to recall the start and end of a long context better than the middle.

🧭 Two practical moves

Because of context rot and "lost in the middle," front-load your most important instructions, and in a long prompt, restate the key constraints near the end. The stuff that matters most should sit where the model pays the most attention.

What is compaction?

Compaction is the cleanup that keeps a long session alive. Instead of carrying every word of the conversation forward, Claude condenses the earlier parts into a compact summary — freeing up the whiteboard while keeping the key facts.

  • What it does: swaps verbose history for a summary so you can keep working in the same session.
  • Why it's needed: it lets you continue past what would otherwise overflow the window — and it pushes back on context rot by trimming the clutter.
  • The catch: compaction is lossy. A summary can drop details the original conversation contained. That's the whole reason for the next section.

Watch the gauge: when to compact

Keep half an eye on how full the window is. In Claude Code you can see context usage as you work; in a chat, watch the length of the conversation and any length warnings.

  • Good moments: a phase of the work is finished, you're about to start a big new sub-task, or you notice Claude's recall starting to slip.
  • Bad moment: in the middle of a delicate, multi-step reasoning chain — compacting mid-thought can drop the very details you need.

And sometimes the best move isn't to compact at all — a crisp summary prompt in a brand-new conversation can beat compacting a bloated thread. (That's the "start fresh" option from Manual Looping.)

Save before you compact

Since compaction is lossy, treat it like saving a document before you close it. Capture the important state first:

  • Have Claude write a handoff doc. Ask it to summarize decisions made, file paths, open questions, and next steps into a document you keep.
  • Persist durable facts to a memory or a skill. Anything that should outlive this session — not just this window — belongs somewhere permanent.
  • Export key artifacts to files. Code, configs, and final drafts should live in a file, not only in the chat.

🛠️ Real Aptera example: the Engineering Team Server Setup

When Jake used Claude Code to build and deploy a new server for the engineering team on Hetzner, it was a long, multi-step session — exactly the kind where the context window fills up. His rhythm:

  1. Watch the window as it grew.
  2. When it got large, have Claude write up the steps so far into a Confluence page (using the Atlassian connector).
  3. Compact — clearing the board, with the work safely documented.
  4. Keep going; when it filled again, have Claude update the same Confluence doc with the new steps plus any extra documentation worth keeping.
  5. Repeat until done.

The payoff: nothing was lost across compaction cycles — and the session ended with a complete, polished setup runbook in Confluence as a byproduct. Documentation he'd have had to write anyway. Two birds, one loop.

Short-term vs. long-term memory

The context window is short-term memory — brilliant within a session, gone after it. For anything that needs to last, reach past the window: Memory, Projects, files, and skills are Claude's long-term memory. Knowing which is which is what lets you work confidently across many sessions without losing the thread. (See Memory & Projects and Connectors & Skills.)

🔑 Key takeaways

  • The context window is finite working memory, measured in tokens — everything you type, paste, attach, and run fills it.
  • Quality degrades as it fills ("context rot"), not just at the limit — so watch the gauge.
  • Compaction frees space by summarizing — compact at natural breakpoints, never mid-thought.
  • Compaction is lossy: save to a doc, memory, or skill before you compact.
  • For knowledge that must last, reach past the window — files, memory, and skills are the long-term store.
